## 1. 文档目的

本文档只补充一类信息：

- 当未来需要新增一个站点能力时，AI Agent 应该如何在**不改变当前项目架构**的前提下完成接手
- AI Agent 应该如何使用真实浏览器、Browser Runtime、扩展和现有调试接口，先自行理解页面，再实现 adapter / workflow
- 哪些问题应由 AI 自主完成，哪些问题应尽早请求人类协助

本文档**不重复**这些内容：

- 正式架构边界：见 `docs/architecture.md`
- 已有开发纪律、排障顺序、新站点扩展顺序：见 `docs/development.md`
- 项目全貌、运行方式、现有能力：见 `README.md`

因此，推荐阅读方式是：

1. 先读 `README.md`
2. 再读 `docs/architecture.md`
3. 再读 `docs/development.md`
4. 如果当前任务是“适配一个新站点”，再读本文档

## 2. 适用范围

本文档适用于以下任务：

- 新增一个此前未接入的站点
- 为新站点增加第一个只读能力
- 为新站点增加新的页面类型识别
- 为新站点增加固定 workflow

本文档不替代以下正式原则：

- 站点 DOM 语义继续放在 `extension/adapters/<site>-adapter.js`
- 固定流程继续放在 `bridge/app/sites/<site>/workflows/`
- Bridge 不承载新的站点 DOM 特判
- skill 不重新接管页面生命周期

## 3. AI 接手时的默认工作方式

未来 AI Agent 接手新站点时，默认采用下面的工作方式：

1. 先确定当前需求属于：
   - 页面类型识别
   - 只读能力
   - 低风险动作
   - 状态变更动作
   - 固定 workflow
2. 先在真实页面里理解 DOM 与页面生命周期，再开始写代码
3. 先做最小可用实现，再补稳定性
4. 先在 adapter 内实现页面语义，再决定是否需要 workflow
5. 遇到宿主态、登录态、扩展刷新等 AI 无法自行闭环的问题时，请求人类协助

这里最重要的一条是：

- **不要先发明抽象；先读懂页面，再做最小落地实现。**

## 4. 新站点适配的 AI 工作流

这一节只描述 AI 额外应执行的步骤；页面类型、ready、只读优先、动作后做 verify 这些正式顺序，仍以 `docs/development.md` 为准。

### 4.1 先做页面侦察

AI 在正式写 adapter 之前，应先完成一轮页面侦察：

- 打开目标站点的关键页面
- 确认至少两类核心页面：
  - 一个详情页
  - 一个列表页
- 记录页面 URL 形态
- 判断该站点是否是明显的 SPA
- 观察页面首屏是否先出壳、后出正文

这一轮页面侦察的目标不是立刻写代码，而是回答：

- `match()` 应该依赖 host 还是更细的 URL 形态
- `getPageType()` 应该怎么区分
- `probeReady()` 是看正文容器、列表项、还是某种页面状态
- 第一个只读能力应该选详情页还是列表页

### 4.2 再做 DOM 研判

AI 应优先用浏览器/底层控制层去理解页面，而不是一开始就猜 selector。

建议固定检查这些信息：

- 关键容器是否存在稳定属性
- 站点是否使用 `data-*`、`aria-*`、结构化链接模式
- 列表项是否有统一卡片根节点
- 详情页正文是否和列表预览共用 DOM 结构
- 页面中是否存在骨架屏、占位块、懒加载节点
- 文本、图片、链接、时间等字段分别落在哪些容器里

如果一个站点明显存在：

- 多层嵌套虚拟列表
- 首屏结构频繁切换
- 同名 class 大量复用
- 列表页与详情页 DOM 相似但语义不同

则 AI 应优先把页面类型识别写清楚，再写提取逻辑，不要试图靠一个宽泛 selector 同时兼容全部页面。

### 4.3 默认先做最小能力

AI 为新站点接入时，默认优先级建议是：

1. 一个稳定的 `match()`
2. 一个稳定的 `getPageType()`
3. 一个不过早误判的 `probeReady()`
4. 一个详情页读取能力或一个列表页读取能力
5. 只有在任务明确需要时，再补 workflow

如果用户只是要求“先接入该站点”，默认建议先做：

- 一个详情页 `read_post` 或同类能力

如果该站点详情页结构比列表页更复杂，也可以先做：

- 一个列表页读取能力

原则是：

- 先选结构最稳定、最容易验证的能力作为第一个落点

## 5. DOM 选择器与提取策略

这一节只补充 AI 在写 adapter 时的具体偏好，不重复正式架构。

### 5.1 selector 选择优先级

默认优先级建议：

1. `data-*` / `aria-*` / 稳定属性
2. 明确的链接模式、语义标签、表单属性
3. 稳定父子结构
4. class 组合
5. 很长的链式 selector

避免默认依赖：

- 明显像构建产物的哈希 class
- 容易随 A/B 测试变化的视觉样式 class
- 过深的祖先链
- 把整页第一个同名按钮直接当成业务按钮

### 5.2 提取逻辑的默认偏好

AI 写提取逻辑时，建议默认遵守：

- 先定位列表项/详情页根容器，再在根容器内做局部查询
- 文本优先提取真正正文，不要把整块容器 `innerText` 全塞进去
- 链接优先保留原始 URL，同时在必要时补规范化
- 图片、视频等媒体先保留页面可见引用，不要在站点适配阶段额外扩大下载逻辑
- 缺字段时允许返回空值，但不要伪造字段

### 5.3 ready 判断的默认偏好

AI 不应只用以下信号判断页面 ready：

- `document.readyState === "complete"`
- 页面有字
- 某个非常宽泛的容器出现

更合理的默认组合是：

- 页面类型已能识别
- 目标正文容器或列表项已出现
- 至少一个关键字段可读
- 必要时参考网络 quiet 状态

如果站点是明显的 SPA，AI 应默认先怀疑“假 ready”，而不是默认相信页面已经稳定。

## 6. 代码落点的默认判断

未来新增站点时，AI 应优先按下面方式落代码：

- `extension/adapters/<site>-adapter.js`
  - `match()`
  - `getPageType()`
  - `collect()`
  - `probeReady()`
  - `read()`
  - 如确有需要再补 `act()` / `verify()`

- `bridge/app/sites/<site>/models.py`
  - 站点 ID
  - read/action/workflow 枚举

- `bridge/app/sites/<site>/site.py`
  - capabilities
  - workflow 分发

- `bridge/app/sites/<site>/workflows/`
  - 只放固定流程
  - 不放站点 DOM 解析规则

- `bridge/app/server.py`
  - 注册新站点

- `extension/manifest.json`
  - 增加站点注入规则

如果 AI 发现自己想把这些逻辑写到 Python 里：

- 页面类型判断
- 站点 DOM 结构解析
- 详情页正文提取
- 列表卡片字段提取

那通常意味着实现已经开始偏离当前架构，应优先回到 adapter 层完成。

## 7. 验证时的默认闭环

本文档不重复已有调试顺序，只补充 AI 在“新站点首次接入”时应重点检查的闭环。

AI 完成第一版实现后，建议至少做下面这几步：

1. 确认新站点页面已注入对应 adapter
2. 确认扩展有最近页面上报
3. 确认 `/site/capabilities` 能识别到正确页面
4. 确认第一个 `read` 能返回结构化数据
5. 如果新加了 workflow，确认其标签页生命周期符合当前项目规则

如果测试结果异常，AI 应优先区分：

- 是浏览器/宿主问题
- 是扩展没刷新
- 是 adapter 没命中
- 是 pageType 错了
- 是 ready 假成功
- 是字段提取 selector 失效

不要一开始就把问题归因成“Bridge 逻辑不够通用”。

## 8. AI 何时应请求人类协助

AI 默认应先独立完成页面理解与第一版实现，但出现下面情况时，建议尽早请求人类协助：

- 目标站点必须登录，且当前账号态不可见
- 目标页面内容因账号、地域、实验分流而明显不同
- 修改扩展后需要人类执行重载扩展与刷新页面
- 需要真实点击、发布、关注、收藏、提交等动作验证
- 需要确认某个页面在业务上到底属于哪种 pageType
- 页面内容受滚动、弹窗、年龄确认、地区限制等交互影响
- 沙箱内看不到宿主浏览器真实状态

请求人类协助时，AI 不应只说“失败了”，而应尽量附上：

- 目标 URL
- 当前页面标题
- 当前推断的 pageType
- 已尝试的 selector / ready 条件
- 是在哪一步失败
- 是否已经确认扩展重载与页面刷新

## 9. 新站点适配的最小交付标准

当 AI 声称“已接入一个新站点”时，最少应满足：

- 至少识别 2 类页面类型
- 至少完成 1 个核心读取能力
- 结果结构基本稳定，不靠一次性选择器侥幸成功
- 已说明代码落点
- 已说明验证方式

如果涉及 workflow，还应额外说明：

- 为什么这是固定流程
- 为什么不应放 skill
- 临时标签页是否会关闭

## 10. 最后原则

未来继续扩新站点时，默认优先以下原则：

1. 先让 AI 用真实页面理解 DOM，再写代码
2. 先做最小可用实现，再补抽象
3. 站点语义继续放在 adapter，不回流到 Bridge
4. 固定流程继续放 workflow，不回流到 skill
5. 宿主态不可见时，优先请求人类协助确认，而不是在沙箱里反复猜

如果后续项目积累出足够多的新站点样本，再考虑提炼更高层的 Adapter Kit；在那之前，先把接入流程标准化，比先做大重构更重要。
